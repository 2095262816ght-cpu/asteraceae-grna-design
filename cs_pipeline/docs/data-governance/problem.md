### 2.1 现象

### 2.2 关键线索：旁边 5bp 处有一条完全合法的 guide

在记录位点旁边找到另一条 guide：`CGTAAGGATTGCTGCTGAGA` + **AGG**（AGG 是合法 NGG，基因组实测吻合）。把基因组序列（负链视角）和两条 guide 对齐：

```
                CCGTAAGGATTGCTGCTGAGA AGG     ← 合法的 guide + PAM
基因组(负链)  ATGAGCCCGTAAGGATTGCTGCTGAGAAGGCCATGG
                     GGATTGCTGCTGAGAAGGCC ATG  ← 表里记的 guide，它的"PAM 位置"落在 ATG 上
```

（上图已按基因组实测坐标核对：两个拷贝（165462909/165502827）的局部序列完全一致，移位 guide 的 revcomp 精确落在 165462914/165502832，即记录 guide 的 5bp 之外。）

可以看出：两条序列共享中间 15bp（`GGATTGCTGCTGAGA`），只是**取的 20nt 窗口错开了 5 个碱基**。记录的那条整体向右挪了 5bp，于是它后面 3bp 的"PAM 槽位"落在了 ATG 上；而正确的窗口再往后 3bp 恰好是 AGG。

### 2.3 通俗理解（给非生物背景读者）

可以类比成一个**字符串取窗口时的 off-by-N 错误**：真实 guide 是基因组字符串里一个固定的 20nt 窗口，PAM 规则相当于"窗口后 3 字节必须是特定后缀（NGG）"的校验。记录者取窗口时起点错了 5 个位置，得到的 20nt 和真实 guide 有 15/20 重叠、看起来像同一条，但校验位（PAM 槽）落到了错误的内容（ATG）上。

真实发生的事很可能是：实际设计/合成、并在实验里高效切割的是 `CGTAAGGATTGCTGCTGAGA`+AGG 这条（或某个移位版本），而填表时把窗口边界记错了 5bp——**indel 数字（1.0）是真的，但数字绑定的序列是错的**。这与第 4 项（USR-5712）是同一类事故。

### 2.4 为什么需关注（对模型的影响）——**后核实：实际未发生，见 2.6 第 3 条**

1. 这 32 行的 `indel_pct=1.0` 是真实数据，若原样进入模型会成为训练标签；
2. 模型学的是"gRNA 序列 → 编辑效率"映射；序列记错 5bp，模型学到的是 **"一条实际无法工作的序列效率 = 1.0"** 的假映射；
3. 这 32 行恰是**全表编辑率 100% 最密集的区域**，权重不小：一小撮高标签 + 错序列，足以带偏模型在高效区间的预测；
4. 特征层面也会错：05 脚本取 PAM 首碱基做特征，记录为 T、实际为 A，特征同样失真。

### 4.0 背景知识（非生物背景读者先读这段）

**4.0.1 DNA 是双链，而且链有方向**

DNA 由两条链组成，两条链的碱基互补配对（A 对 T、C 对 G），并且走向相反（一条 5'→3'，另一条 3'→5'）。习惯上把基因组发布的那条链叫**正链（+）**，它的互补链叫**负链（-）**。

因为互补 + 反向，知道一条链的序列就能推出另一条：把序列每个碱基换成互补碱基、再整体倒序，这个操作叫**反向互补（reverse complement）**。例如：

```
正链  5'-GAAAATATTGAAAACATATA-3'
负链  3'-CTTTTATAAGTTTGTATAT-5'   ←→  按 5'→3' 习惯写出来就是 5'-TATATGTTTTCAATATTTTC-3'
```

所以同一个 DNA 位点，从正链看和从负链看是**两条完全不同的字符串**。这是本项一切混乱的根源。

**4.0.2 Cas9 切割的硬规则：20nt 向导 + 紧跟的 NGG PAM**

Cas9 蛋白在 guide RNA（gRNA，20nt）的引导下结合 DNA，但有个前提：这 20nt（叫 protospacer）的**紧下游 3bp 必须是 NGG 模式**（N=任意碱基，后两位必须是 GG），这 3bp 叫 **PAM**。没有合法 PAM，Cas9 根本不结合、不切割。切割发生在 PAM 上游约 3bp 处，之后细胞修复切口时会产生小插入/缺失（indel）——**indel 就是"编辑成功"的信号**。

记录约定：一条 guide 记作 `protospacer(20nt) + PAM(3bp)`，如 `GAAAATATTGAAAACATATA`+`TGG`。

关键推论——**同一位点从负链看，PAM 会变成 CCN**：假设正链是 `5'-...N20-NGG...-3'`，那么负链按 5'→3' 读就是 `5'-...CCN-N20的反向互补...-3'`（NGG 的反向互补是 CCN，且跑到了protospacer 的左边）。所以"在基因组浏览器正链上看到 CCN"就等于"这个靶点的 protospacer 和 PAM 其实在负链上"。两种写法描述的是**同一个靶点**，只是观察方向不同；但记录时必须统一用一种约定（本项目用 NGG 约定），否则下游程序会当成两个不同的位点。

**4.0.3 "基因在哪条链"和"guide 打哪条链"是两回事**

基因有方向（转录方向），LG07.3296 这个基因在负链上。但 Cas9 切割不看基因方向——guide 打正链还是负链都能切，只要满足 NGG 规则。所以"基因在负链"不构成"guide 必须在负链"的理由；同理，**一条 guide 记录在正链还是负链也没有对错之分**，只要序列和它旁边的 NGG PAM 对得上基因组就是合法记录。

**4.0.4 Hi-TOM 测的是什么、indel_pct 怎么算出来的**

Hi-TOM 是靶向扩增子测序：对每棵植株，用 PCR 把靶点周围约 300-400bp 的片段（amplicon）扩增出来高通量测序，再和一条**提交时给定的参考序列**比对，看切口附近有没有 indel。公司结果把每条 read 按比对位置拆成"左（Left）/右（Right）"两段，标注变异类型（WT=无变异、1I=插入1bp、5D=缺失5bp、SNP、Large_Indel 等）。

本表统一的统计口径（经 11 个已知值交叉验证，见"一、已解决 8"）：`indel_pct = 左侧非WT的reads数 / 总reads数`。这个口径隐含一个前提——**切割点位于参考序列展示方向的左侧**。参考序列按哪个方向提交，决定了切割信号落在输出表的"左"列还是"右"列。

### 4.2 查明的事实（含推理过程）

**事实 1：这批的测序结果是按负链方向展示的，而且根源在提交参考时就是负链。**

表里记录的 guide 是 `GAAAATATTGAAAACATATA`+TGG，但 5712 原始结果的 reads 里出现的是它的反向互补 `TATATGTTTTCAATATTTTC`，PAM 以 CCA 的形式出现——即同一位点从负链看的样子（见 4.0.1/4.0.2）：

```
基因组正链  5'-...TGA GAAAATATTGAAAACATATA TGG...-3'   （LG07:109029051-076）
5712结果里  5'-...CCA TATATGTTTTCAATATTTTC TCA...-3'   （同一序列的负链视角）
```

对照 USR-5713 批：结果里直接能看到 guide `GGCGTTAGATTGACAGAAGA`+CGG，是正链方向展示。两批的展示方向正好相反。（公司 report 每行备注"参考序列反向互补，请重新提交"，但 5713 的报告里也有同样备注，是通用模板话，不能当判别依据；reads 序列本身是硬证据。）

**根源**：团队自己保存的提交参考文件（`data/raw/hitom/R0_sequencing/20211224_transgenic_seedlings/Reference - 21.12.31.txt` 与 `data/raw/hitom/R1_sequencing/unsorted/re-2022.6.14.txt`）中的 `>SP3` 参考（295bp）经比对即为正链 109028842-109029136 的反向互补。即不是测序公司搞反方向，而是**提交参考时用的就是负链序列**，公司备注指的正是这件事。

**事实 2：整理进 Sheet1 时已经做过正确的链向转换——"抄错方向"这个简单解释被排除。**

面对一份负链展示的结果，整理者当时有两种填法：

```
看到的(负链视角)  5'-...CCA TATATGTTTTCAATATTTTC TCA...-3'

填法 A（照抄看到的）:     seq-20 = TATATGTTTTCAATATTTTC, pam = CCA
填法 B（换算成正链约定）:  seq-20 = GAAAATATTGAAAACATATA, pam = TGG   ← 表里实际是这个
```

表里写的是 B，说明整理时**做过反向互补转换，且转换本身没错**。这是逐字字符串比对的事实，不是推断：B 版本在基因组正链 109029054 逐字命中、下游紧跟 TGG（合法 NGG）；而 A 版本在整个基因组里**不存在**——如果真抄错了方向，表里应该是 A。

事实 2 的意义是排除最简单的假设：如果错误只是"链向抄反"，改正只需一次反向互补。但真相更微妙（见事实 3）。注意区分两件事：**"记录的字符串是正链序列"（事实）≠"该记录就是真实被测的 guide"（不是，见事实 3）**。

（strand 列说明：旧记录中这 61 行 strand=`-`，若理解为"guide 所在链"则与正链 guide 矛盾，若理解为"基因所在链"则成立（LG07.3296 确在负链，GFF 确认）；当时因全表 491 行均为 `-`（第 1 项）未改动——第 1 项已于 2026-09-16 由基因组证据判定为整列填充错误。9.15 改正后该问题自动消解：真实 guide 就在负链，两种理解下 `-` 都正确。）

**事实 3（核心问题）：真正被切割的不是表里记的那个位置，而是上游 170bp 处负链上的另一条 guide。**

判断依据是 Cas9 的铁律：**切割点固定在 PAM 上游约 3bp，切口周围的 reads 必然留下 indel 痕迹**——只要在 reads 里找到 indel 聚集的位置，就知道 Cas9 实际切了哪。结果：

- 表内靶点的切割点（109029070/071 附近）在全部 61 个样本里**全是 WT，零编辑**——记录的那条 guide 实际上没切任何东西；
- 全部 indel 都集中在上游约 **170bp 的另一位点**（正链 109028897-916），而且这个位点的 protospacer 在**负链**上：

```
正链  5'-...CCT TCAGGCATCCTGACATTTTC...-3'
          ↑↑↑ 这就是"负链上的 CCN"在正链上的样子
负链  5'-...GAAAATGTCAGGATGCCTGA AGG...-3'
              └── 真实 protospacer ──┘ PAM
```

负链 protospacer `GAAAATGTCAGGATGCCTGA`+PAM `AGG` 在全基因组唯一，预测切割点 ≈109028899；观测到的删除段与之精确吻合（16D 删 109028894-909、5D 删 109028892-896——切割点正在两者之间）。单样本编辑比例最高约 70%，说明真实那条 guide 效率很高。

记录序列 `GAAAATATTGAAAACATATA` 与真实序列 `GAAAATGTCAGGATGCCTGA` 都以 `GAAAAT` 开头、且位于同一段 amplicon 内——**整理时把同一片段里两条 GAAAAT… 序列张冠李戴了**。也就是说：不是链向抄反（事实 2 已排除），而是**从结果里挑序列时挑错了对象**。

**事实 4：indel 数字被"口径前提被破坏"系统性低估。**

如 4.0.4 所述，统一口径"左侧非WT"隐含"切割点在展示方向左侧"的前提。这批 amplicon 方向反了（事实 1），真实切割点落在输出表的**右侧**——于是：

- 左列只有 WT 和天然 SNP，大多数样本算出 ≈0；
- 只有大段缺失（Large_Indel 会被公司同时写进左右两列）漏进左列，被计上 0.41~0.70；
- 旧版"28 行全 0"就是这么来的——不是没编辑，是**口径看错了方向**。类比：解析日志的程序写死"取第 2 列"，而这个文件的列是镜像排列的。

（当前 61 行 indel 与左口径复算吻合，58/61 一致；按切割点所在侧（右）重算后：中位数 0.0123→**1.0**，均值 0.053→0.778，详见 4.6。）

### 4.3 总结：三层问题叠加

| 层 | 问题 | 后果 |
|---|---|---|
| ① 记录层 | 整理时把同一 amplicon 里两条 GAAAAT… 序列记混（事实 3） | 表内 seq-20/pam/坐标不对应任何真实编辑 |
| ② 提交层 | 参考序列按负链提交（事实 1） | 输出表左右方向与其他批相反 |
| ③ 统计层 | 统一口径假设"切割点在左"（事实 4） | 该批 indel 被系统性低估（旧版全 0） |

一句话：**indel 数字是真的，但数字绑定的序列是错的**（与第 2 项同类）；方向问题本身不影响切割，只影响了统计口径。
